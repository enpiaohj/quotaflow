## 二、P0：必须优先处理

### P0-1 建立远程仓库备份

**证据**：`git remote -v` 输出为空。9 个已发布版本、约 14,500 行代码、全部 Release 快照
**只存在于这一块硬盘上**，没有任何异地副本。

**风险**：硬盘故障或误删即全部丢失。这是当前项目最大的单点风险，且与代码质量无关。

**动作**：
1. 建立私有远程仓库（GitHub Private / Gitee 私有 / 自建 Git 均可）。
2. push 前确认 `.gitignore` 已排除 `publish/`、`bin/`、`obj/`、`*.qfbackup`，
   并用 `git log -p | grep -i` 抽查历史提交中是否混入过密钥。
3. `git push --tags` 把 v1.0.0～v0.9.1 全部 tag 推上去。

**工作量**：半天（主要花在历史密钥抽查上）。

**注意**：`git push` 属于需要明确授权的操作，执行前会先确认。

---

### P0-2 App 层业务逻辑下沉到 Core，使其可被测试

**证据**：本次会话中两个最严重的缺陷都在同一个文件里——`SettingsViewModel.cs`
（1,053 行，全项目最大）：

| 缺陷 | 后果 | 能否单测 |
| --- | --- | --- |
| 保存设置重置整个 `WindowDisplay` | **数据丢失**：显示模式、不透明度、置顶、各显示器记住的窗口位置全部回默认 | ❌ |
| `BuildSettingsSnapshot` 从零构造对象 | 上一条的根因；将来任何新增字段都会重蹈覆辙 | ❌ |

这两个缺陷只能靠 UI 自动化加窗口截图验证，成本高、且**只在我恰好想去测的时候才会被发现**。
测试工程当前只引用 Core（见 `QuotaFlow.Windows.Tests.csproj`），App 层 2,364 行 ViewModel
代码零覆盖：

```
SettingsViewModel.cs      1053 行
MainPanelViewModel.cs      469 行
CustomPlatformRow.cs       273 行
ProviderCardViewModel.cs   207 行
其余                       412 行
```

**方案（推荐）**：把"规则"从 ViewModel 下沉到 Core，而不是想办法去测 WPF。

1. 新增 `Core/Services/SettingsSnapshotBuilder`：接收"设置页拥有的字段值"与"磁盘基线"，
   返回要写回的 `AppSettings`。**这正是 WindowDisplay 缺陷的所在**，下沉后可直接写测试：
   "设置页不拥有的字段必须原样保留"。
2. 同类可下沉的还有：平台可见性解析（`HiddenPlatforms` → 卡片可见性）、
   自定义平台行校验（`IsValidCustomPlatform`）、脏数据比对逻辑。
3. ViewModel 只保留绑定与命令编排。

**备选方案（不推荐先做）**：让测试工程引用 App。需要把 TFM 改成
`net8.0-windows10.0.19041.0` 并处理 WPF 的 STA 线程要求，收益不如下沉明确，建议后置。

**工作量**：2–3 天。

**验收**：新增测试能覆盖"保存设置不得动窗口显示设置"这条规则；故意破坏该规则时测试必须失败。

## 三、P1：应尽快处理

### P1-1 三个未验证项收口

以下修复均已发布，但**未在真实条件下确认**，需要各自的验证路径：

| 项 | 版本 | 未验证的原因 | 如何确认 |
| --- | --- | --- | --- |
| Claude 限流退避 | v0.8.0 | 无法主动触发 Anthropic 的 429 | 下次出现时看提示是否变成「将在 N 分钟后自动重试」，且额度数字仍在 |
| 代理修复 | v0.9.1 | 无法在出问题的那台机器上实测 | 在该机器改为「直连」；若仍失败，看新提示里带的代理地址 |
| `per1WeekPercentage` 语义 | v0.6.0 | 阿里云无公开文档 | 与百炼控制台页面显示的百分比比对 |

**动作**：在 README 或 CHANGELOG 中维持一份"待确认清单"，确认一项划掉一项，
不要让它们无声无息地留在代码里。

**工作量**：随遇随做。

---

### P1-2 内置诊断报告

**证据**：本次会话中，几乎每个问题都需要临时搭诊断设施：

- 网络代理问题 → 临时写 `qf-net-diag.ps1`（且第一版因编码、第二版因参数用法两次返工）
- 百炼接口失效 → 临时加 `diag-tokenplan` / `diag-gateway` / `diag-newapi` / `diag-js` 等 6 个命令
- 设置页缺陷 → 临时写 UIA 脚本 + 窗口截图

这些全部是一次性的，用完即删。同类问题下次仍要从零再来。

**动作**：设置页「数据与隐私」新增「生成诊断报告」，一键输出到文件：

```
应用版本 / 系统版本 / 是否 RDP 会话
当前代理来源与实际代理地址
各平台最近一次的 ProviderState 与 ErrorCategory（不含额度数值）
各平台端点的连通性探测结果
crash.log 最近 N 条的异常类型（不含堆栈细节）
```

**硬性要求**：报告绝不能包含 API Key、Cookie、SEC_TOKEN、额度数值。
生成后在界面上明确告知"报告已脱敏，可安全发送"。

**价值**：用户自助定位；反馈问题时一次给全信息，避免多轮往返。本次代理问题若有此功能，
排查可从数轮缩短到一次。

**工作量**：1 天。

---

### P1-3 百炼接口脆弱性防护

**证据**：Token Plan 走的是控制台内部接口（非公开 API），本次已经历过一次完整失效排查：
网关地址、`action`、`product`、请求体构造、`sec_token` 位置全部需要靠抓包逆向确认。
阿里云随时可能再改。

**动作**：
1. 把已确认的请求形状（`params` 信封含 `cornerstoneParam`、`sec_token` 在 body、
   `api` 参数不编码）固化为测试——已有部分，补齐剩余。
2. 响应结构校验失败时，提示明确区分"登录态失效"与"接口已变化，请反馈给开发者"，
   后者附上足以定位的结构信息（字段名，不含值）。
3. 在 README 的「已知风险」中写明该接口非公开、可能随时失效。

**工作量**：1 天。

## 六、过程改进（本次会话的教训）

以下四条是我在本次会话中**实际犯过的错**，记录下来避免重复：

1. **构建必须看退出码，不能只 grep 错误关键字**
   曾用 `grep "error CS"` 过滤构建输出，恰好把文件占用错误 `MSB3021` 滤掉，
   空输出被误读成"构建成功"，导致后续一整轮验证跑的是旧二进制。

2. **UI 改动必须运行时验证**
   两个缺陷编译 0 错误 0 警告、XAML 也能解析，但功能是坏的：
   自定义 `Expander` 模板缺 ToggleButton（点了不展开）、
   `TabControl` 内容宿主未命名 `PART_SelectedContentHost`（右侧整片空白）。

3. **UIA 枚举结果不可轻信，截图才是判据**
   曾因 UIA 对滚动区外元素返回不完整结果，误判"取消隐藏不生效"并准备修一个不存在的缺陷；
   截图后发现功能一直正常。另有一次断言写成 `-notcontains` 而集合为空，平凡通过报了假的成功。

4. **对照实验的结论要克制**
   曾因"伪造 action 与不带 Cookie 的对照组返回完全一致"推断百炼网关地址已废弃，
   实际只是请求体不完整、在网关层被统一拒绝。这个误判导致绕了数轮。
   **相同的失败响应只能证明"在同一层被拒"，不能证明"地址失效"。**

5. **给用户的脚本先自测**
   诊断脚本第一版因 BOM 编码在 PowerShell 5.1 上无法解析，第二版 B 组因
   `-ProxyUseDefaultCredentials` 参数用法错误从未真正执行。此后改为先在本机跑通再发出。

### 执行中的额外发现

P0-2 过程中挖出一个**比原计划目标更严重的缺陷**并已修复（v0.9.2）：
窗口显示设置一直在静默丢失——界面生效、磁盘未写、重启回退，且没有任何提示。
根因是 WPF 的 `Window.Width/Height` 为 `NaN` → `System.Text.Json` 抛异常 →
`SaveCore` 静默吞掉。这印证了本计划 P0-2 的判断：这类缺陷正是藏在无测试覆盖的 App 层。

### 需要更正的一处记录

执行 P0-2 时我曾宣布"确认 `MoveCard` 存在数据丢失缺陷"，**该结论是错的**：
重启后显示模式回到 TrayPopup 是设计行为（`RestoreLastModeOnStartup` 默认关闭时每次启动
强制切回），与 `MoveCard` 无关。`MoveCard` 改用读-改-写属于结构性加固，不是已确认缺陷的修复。

这正是本文档第六节第 4 条教训（对照实验的结论要克制）的又一次重演。补充一条新教训：

6. **从界面推断磁盘状态不可靠。**
   当天在"设置到底存没存下来"上反复误判，直到直接解密读取设置文件才拿到可靠事实。
   涉及持久化的验证应当直接读存储，而不是看界面显示什么。

### P2-1 暂缓的理由

本计划自己写明的前置条件是「先下沉逻辑并补上测试，再动结构，否则拆分过程没有测试保护」。
到目前为止 `SettingsViewModel` 仍**没有任何直接测试**，纯代码搬运只有编译器兜底；
而 `SettingsWindow.xaml` 拆 `UserControl` 的错误只在运行时暴露——当天已经因此栽过两次
（自定义 `Expander` 模板缺 `ToggleButton` 导致点了不展开、`TabControl` 内容宿主未命名
`PART_SelectedContentHost` 导致右侧整片空白，两者编译都是 0 错误 0 警告）。

为纯组织性收益承担运行时风险不划算。该项保留，前置条件是：
ViewModel 的关键行为获得测试覆盖（可继续沿用 P0-2 的做法——把规则下沉到 Core，
而不是想办法去测 WPF）。

## 走向 1.0 的条件

当前 0.x 的原始理由（「百炼 Provider 尚未稳定」）自 v0.6.0 端到端跑通后已不成立，
但仍不宜直接跳 1.0——1.0 意味着对外承诺稳定性，而下列几项尚未成立：

- [x] **待确认清单清空**（2026-09-01 由使用者确认）
      Claude 限流退避、代理修复、`per1WeekPercentage` 语义三项均已在真实条件下验证通过。
- [ ] **多机验证**
      当天的两个严重缺陷（跨机器网络失败、窗口设置静默丢失）都说明单机验证不足以支撑
      稳定性承诺。至少需要在两台不同机器上各跑一轮完整功能。
- [ ] **App 层关键行为有测试覆盖**
      即 P2-1 的前置条件。当天两个数据丢失级缺陷都出在无覆盖的 App 层，这不是巧合。
- [ ] **连续运行观察**
      至少一周日常使用无新增数据丢失类问题（诊断报告的「最近异常类型」可作为观察窗口）。

满足后再评估是否发 1.0.0。**不设时间表**——条件不满足就继续留在 0.x，
版本号本来就是用来如实表达状态的。
